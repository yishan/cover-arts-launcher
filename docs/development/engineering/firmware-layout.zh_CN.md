# 固件布局

本 Launcher 面向 ESP32-C3、8 MB Flash。完整系统固件以空动态玩法库启动；浏览器玩法管理器
根据每个已校验玩法的实际大小，向分区表动态加入 OTA 条目。

## 空 Launcher 布局

| 分区 | 类型／子类型 | 偏移 | 大小 | 用途 |
| --- | --- | ---: | ---: | --- |
| `nvs` | data/NVS | `0x9000` | `0x6000` | Launcher 与玩法键值数据 |
| `phy_init` | data/PHY | `0xF000` | `0x1000` | PHY 初始化数据 |
| `factory` | app/factory | `0x10000` | `0x170000` | Launcher，最大 1,507,328 bytes |
| `otadata` | data/OTA | `0x7FE000` | `0x2000` | 标准 ESP-IDF 启动选择数据 |

动态玩法区域为 `0x180000..0x7F0000`。每个已安装玩法对应连续编号的 `ota_0..ota_15`
条目；删除玩法后，物理地址可以不再与逻辑顺序一致。每个分配范围由“玩法 App 实际长度向上按
64 KiB 对齐”加上分区尾部 64 KiB DPS1 Sidecar 组成。Sidecar 以双 bank 保存身份元数据和封面。
所有范围不得重叠或越出玩法区域。

删除玩法时，只重写后续玩法的逻辑身份，不复制保留玩法的 App 数据。后续安装优先使用能够容纳
玩法的最小释放空间，再使用尾部空间。v1.5.0 不执行碎片空间的物理整理。

## 镜像类型

- **完整系统合并镜像**从 `0x0` 开始，包含 bootloader、空动态分区表和 factory Launcher，
  用于首次迁移或主动完整刷新。
- **App-only 镜像**以 ESP 应用镜像开头，经校验后写入新分配的动态 `ota_*` 条目；绝不能把它
  从 `0x0` 写入。
- 兼容的玩法合并镜像只有在分区表和内嵌 App 均通过校验并成功提取后才能安装。普通玩法安装
  不重写 bootloader、NVS、PHY、factory Launcher 或其他玩法范围。

完整系统镜像可能是稀疏的，因此不能证明动态玩法区域已经为空。首次安装必须明确擦除并校验
`0x180000..0x7F0000` 与 `otadata`，才能报告空玩法库。

## 强制校验

运行 `./tools/validate.sh --firmware`。门禁使用隔离目录构建合并镜像，根据 `flash_args` 校验
偏移，并检查分区表 MD5、分区边界、不重叠和 factory App 是否适配。Host tests 还覆盖空动态
分区表、64 KiB 分配规则、16 条目上限、逻辑重排、最小适配空洞复用和 8 MB 边界。CI 使用同一
套门禁。

完整系统固件与子玩法固件必须作为不同产物发布。`build/FoloToy-AI-Passport.bin` 是 factory
Launcher 的 App-only 镜像，不是完整系统镜像，也不是子玩法镜像。

## 写入与数据

写入新固件前，不要求备份设备里原有的固件；但这不代表用户数据会被保留，也不构成整片擦除
授权。必须保留的设置、记录或其他数据应先导出。

从旧固定位置或单 factory 布局迁移时，会重写分区表并改变 Flash 地址含义。已验证的合并镜像
从 `0x0` 写入；它会填充分段间隙，可能重置 NVS 或 PHY，同时不会自动清空动态玩法区域。因此
迁移应使用经过审核的完整安装流程，由它明确擦除并校验玩法区域和 `otadata`。

日常开发可在明确当前分区布局和写入目标时使用分段 `idf.py flash` 保留兼容 NVS 数据。
`idf.py erase-flash` 会清除全部用户数据，不是常规前置步骤。
