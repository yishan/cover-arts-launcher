# 动态玩法存储 v0.3 设计

状态：Launcher 运行时已实现并完成真机测试；网页集成由独立流程维护

目标版本：v1.3.1

兼容性：从 v0.2 固定三个位置迁移时需要变更 Flash 布局

## 目标

玩法管理器不再为每个位置预留固定 2 MiB，而是按已校验 ESP App 的实际长度分配空间。玩法依次追加，直到剩余连续空间无法容纳下一个 App 及其 Sidecar。面向用户的位置仍是稳定、有顺序的玩法库；物理偏移和大小不向普通用户暴露。

本方案继续使用 ESP-IDF 标准 Bootloader、`otadata` 和 OTA 分区 subtype，不要求第三方玩法修改，也不引入自定义 Bootloader。

## Flash 契约

从 Flash 起始到 factory Launcher 的系统前缀保持固定。动态玩法分区使用按 64 KiB 对齐的 `0x180000..0x7f0000`；标准 `otadata` 保持在 `0x7fe000..0x800000`。由于 App 分区采用 64 KiB 分配单元，`otadata` 前的小段空间有意不分配给 App。

每个玩法分区包含：

```text
分区开始
  已校验 ESP App 镜像
  擦除状态的对齐填充
  64 KiB 位置 Sidecar
    封面 payload
    双 bank manifest／信任／安装记录
分区结束
```

64 KiB Sidecar 在 v0.3 中采用以下布局：

| 相对范围 | 内容 |
| --- | --- |
| `0x0000..0x95ff` | 一份 120×160 RGB565 封面 payload |
| `0x9600..0x9fff` | 擦除状态的填充 |
| `0xa000..0xafff` | 元数据 bank A |
| `0xb000..0xbfff` | 元数据 bank B |
| `0xc000..0xffff` | 保留并保持擦除状态 |

每条元数据记录绑定位置、精确 App 长度和 SHA-256，同时保存标题、Source ID、版本、安装历史和封面 CRC。A/B 元数据按 generation 选择。封面 payload 损坏或写入中断时回退到占位图，但不会让独立 CRC 保护的常驻 App 记录失效。

分配公式：

```text
align_up(已校验镜像长度, 64 KiB) + 64 KiB Sidecar
```

生成的分区仍是标准 `app/ota_N`。Sidecar 位于 ESP 镜像实际长度之外、玩法分区边界之内，由 Launcher 和玩法管理器管理；玩法不得写入自身正在运行的 App 分区。

ESP-IDF 定义了 `ota_0` 至 `ota_15`，因此目录绝对上限为 16 个玩法；通常会先受 Flash 容量限制。

## 追加事务

第一版采用只追加模式，只接受紧凑、连续的 `ota_0..ota_N`：

1. 校验传入的 ESP32-C3 镜像并取得精确镜像长度。
2. 读取并验证当前分区表及全部动态条目。
3. 计算对齐后的分区和 Sidecar 边界。
4. 连续空间不足时，在任何擦除操作前拒绝。
5. 把 App 写入未使用 Flash，校验 checksum、appended SHA-256 和读回哈希。
6. 写入并验证 Sidecar。
7. 生成并验证只新增一个条目的分区表。
8. 提交分区表、清空 `otadata`，复位回 factory Launcher。

在第 7 步提交前，旧分区表仍完整描述现有玩法库；此前断电最多留下不可达数据。提交主分区表扇区期间断电仍可能要求进入 ROM 下载模式恢复，玩法管理器必须明确提示该边界，并保留完整系统恢复入口。

## 更新与删除策略

- 相同或更小的更新可以在完整校验 App 和 Sidecar 后复用原分区。
- 最后一个分区可以向空闲尾部扩展。
- 中间玩法变大时，把新版追加到尾部，再提交逻辑目录；物理移动不得重置首次安装时间和启动次数。
- 删除最后一个玩法立即回收空间。
- 删除中间玩法第一版保留空洞；v0.3 分别显示总空闲空间和当前最大可安装连续镜像。
- 整理空间属于后续显式操作，不得在普通启动过程中自动执行。

## 设备与网页变化

Launcher 必须在运行时枚举连续 OTA 条目，不再编译固定三个元素的数组。模型容量上限为 16，实际数量由运行时确定。Cover Art 仍显示上一张、当前张和下一张，位置指示改为“当前 / 总数”。

添加新玩法时，玩法管理器不再要求用户选择物理位置，而是显示本次需要、当前剩余和安装后剩余容量，随后自动追加。更新与删除仍明确显示目标玩法名称和稳定 Source ID。

玩法数量增加后，Launcher 开机不能再计算所有完整 App 的 SHA。开机先读取小型 Sidecar 目录，只在启动所选玩法或用户主动诊断时执行完整镜像校验。

## 迁移

v0.2 固定三位置表和 v0.3 动态表是两种不同系统布局。普通玩法安装不得在两者之间改写。玩法管理器识别 v0.2 后，需要说明迁移会重建玩法库，并进入专用完整系统迁移流程。

首个安全版本要求用户迁移后重新安装现有玩法；自动搬运玩法要等到完成断电真机测试后再提供。
